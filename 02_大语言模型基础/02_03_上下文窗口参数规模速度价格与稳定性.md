# 02 03 上下文窗口 参数规模 速度 价格与稳定性

## 核心原则

模型选型不是选“最强模型”，而是：

> 在质量、安全、延迟和成本约束下，选择最适合当前任务的方案。

## 1. 上下文窗口

上下文窗口是模型一次调用中可同时处理的 Token 总量，通常包括：系统指令、用户问题、历史对话、检索资料、工具结果和模型输出。

窗口长不代表模型会自动准确利用所有信息。超长或杂乱上下文可能增加成本、延迟、遗漏和冲突风险。

## 2. 参数规模

参数规模是模型容量的一个因素。较大模型可能在复杂语言理解、代码或推理任务上更有潜力，但不保证每个任务更好。

更大模型还可能带来更高成本、更慢响应和更高部署要求。固定字段提取、简单分类等任务不一定需要最大模型。

## 3. 速度 延迟与吞吐量

- **延迟**：用户提交后多久收到可用结果。
- **吞吐量**：单位时间内系统可以完成多少任务。
- **完成时限**：一批任务必须在何时前处理完。

实时客服重视低延迟；夜间批量处理更重视吞吐量和次日完成时限。最终体验还受检索、文件解析、工具调用、网络和重试影响。

## 4. 成本

总成本不只包括模型单次调用价格，还包括：输入/输出 Token、检索、文件解析、工具调用、重试、监控、评测、人工复核和错误造成的业务成本。

“单次调用便宜”不等于“整体成本低”。

## 5. 稳定性

稳定性包括：

- 同类输入是否稳定获得相近质量；
- 是否稳定遵循格式；
- 服务是否可用；
- 模型版本更新后是否发生回归；
- 高峰期是否限流、超时或失败。

## 6. Temperature

Temperature 控制生成时的随机性和多样性：

- 较低：通常更稳定，适合提取、分类、固定格式输出；
- 较高：通常更多样，适合创意和头脑风暴。

低 Temperature 不保证事实正确。事实正确性依赖资料、检索、工具验证、评测与人工复核，而不是仅靠降低随机性。

## 模型选型清单

1. 任务质量标准是什么？
2. 是否需要长上下文、图片、文件、音频或工具调用？
3. 用户能等待多久？
4. 单次和整体成本能否接受？
5. 数据是否允许发送给该服务？
6. 出错后如何降级、重试和人工接管？

## 小测试

1. 为什么参数更大的模型不一定是最佳选择？
2. 夜间处理 5000 条客服对话时，延迟和吞吐量应如何权衡？
3. Temperature 主要控制什么？为什么不能保证事实正确？
4. 从 PDF 合同提取字段时，优先关注哪些能力？

## 参考答案

1. 还要看任务质量、成本、延迟、上下文、多模态能力、安全和稳定性。
2. 优先保证总吞吐量与完成时限；单条不必像实时交互那样极快。
3. 控制随机性和多样性；它不提供事实验证和最新资料。
4. 文件理解、字段准确性、结构化输出、隐私权限、异常处理与人工复核。

## 验收标准

- [ ] 能从质量、成本、延迟、数据安全等角度比较模型。
- [ ] 知道长上下文不是万能方案。
- [ ] 能区分实时延迟与批处理吞吐量。
